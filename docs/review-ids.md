# レビュー観点の ID (このキットで使うもの)

レビューコメントには観点の ID を添える。ID があると、受け手は根拠の説明を待たずに何を直せばよいか分かる。
ここに載せるのは **このキットが使う ID と、その一般的な言い換え** だけ。
所属組織にレビュー観点集があれば、同じ ID の本文を正とする。無ければこの表をそのまま使う。

## 温度感タグ

コメントの先頭に付ける。

| タグ | 意味 |
|---|---|
| `[MUST]` | 直さないとマージしない。理由を括弧で添える (例: `[MUST] (秘密がリポジトリに入るため)`) |
| `[SHOULD]` | 直してほしい。理由付きの見送りや別タスク化は可 |
| `[NITS]` | 任意。好みや細かな修正 |
| `[Q]` | 質問。指摘ではない |
| `[MEMO]` | 作者による判断の記録。返信不要 |

MUST にするのは次のどれかに当たるときだけ: マージすると壊れる / 環境差で本番で動かない / 運用ルール違反 / 要件との不一致がマージで「完了扱い」になる / セキュリティや権限の欠陥。どれにも当たらなければ SHOULD 以下。

## 使う ID

| ID | 一般的な言い換え | 出る演習 |
|---|---|---|
| DESC-01 | PR の説明が、実際の変更の規模と内容を過不足なく示しているか | 04, 08 |
| DESC-05 | 背景・変更・影響範囲・確認方法が書かれ、第三者が再現できるか | 04 |
| SCOPE-01 | PR のタイトルと中身が一致し、1 つの目的に収まっているか | 04 |
| SCOPE-02 | ローカル専用のファイル (エディタ設定など) がコミットに混ざっていないか | 08 |
| REQ-01 | 実装が依頼や仕様の規定と一致しているか。食い違うならどちらを直すか決めたか | 05 |
| REQ-05 | 仕様に無い見た目や挙動の変更が、申告なしに混ざっていないか | 08 |
| ENV-04 | ローカルパスや環境固有の値が差分に混ざっていないか | 08 |
| SEC-02 | 秘密 (鍵、トークン、パスワード) がリポジトリや成果物に入っていないか | 08 |
| DOC-01 | コメントの内容が実際の処理と合っているか | 08 |
| STYLE-01 | 画面に出る文言に誤字がなく、体裁が崩れていないか | 08 |
| STATIC-04 | class 名や id の綴りが HTML と CSS で一致しているか (違えばスタイルが当たらない) | 08 |
| STATIC-06 | 装飾目的で見出しタグ (h2, h3 など) を使っていないか | 08 |
| STATIC-09 | 固定の高さを指定せず、内容に応じて伸びるか (`min-height`) | 08 |
| STATIC-10 | 画像に内容を表す alt があるか (装飾画像は `alt=""`) | 08 |

## コメントの書き方

1. 1 コメント 1 論点。複数あれば番号を振る
2. 根拠を添える (再現手順、行番号、一次情報へのリンクのどれか)
3. 直し方を示せるなら示す
4. 判断を受け手に委ねるときは、委ねると書く (「判断はお任せします。このまま進めるなら Resolve してください」)
5. 推測は「おそらく」と明示する
