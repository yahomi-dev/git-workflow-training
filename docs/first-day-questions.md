# 現場の初日に聞くこと

研修で覚えた流れは「既定の 1 つ」でしかない。現場ごとに違う。
初日に下の空欄を埋める。答えが無い項目は「決まっていない」と書く (それも答え)。
演習 11 では、このファイルの空欄を自分の言葉で埋めた PR (GitLab では MR) を出す。

## 聞くこと

各項目は「聞く理由」1 行と、答えを書く空欄。

### ブランチとコミット

- ブランチ運用は何か (GitHub Flow か。`develop` ブランチがあるか。git-flow か)
  - 聞く理由: どこから切ってどこへ PR を出すかが変わる。間違えると PR をまるごと出し直す
  - [ ] 答え: 
- ブランチ名の規則は何か (チケット番号を入れるか。`feature/` などの接頭辞)
  - 聞く理由: チケット連携や CI がブランチ名を見ていることがある
  - [ ] 答え: 
- コミットメッセージの規約は何か (Conventional Commits か。チケット番号。日本語か英語か)
  - 聞く理由: changelog を自動生成する現場では、形式がずれると拾われない
  - [ ] 答え: 

### PR とレビュー

- マージ方式は何か (squash / rebase / merge commit)。PR の粒度はどのくらいか
  - 聞く理由: squash ならコミットは荒くてよい。rebase や merge commit ならコミットを整えて出す必要がある
  - [ ] 答え: 
- PR テンプレートはあるか。レビューは何人か。approve は必須か
  - 聞く理由: 誰の approve を待てばマージしてよいかが分からないと止まる
  - [ ] 答え: 
- CI はどこで見るか。赤くなったら誰に聞くか
  - 聞く理由: 自分の変更と無関係に赤くなることがある。1 人で抱えると時間が溶ける
  - [ ] 答え: 
- マージされた変更はいつ、誰がリリースするか (タグを打つか。自動デプロイか)
  - 聞く理由: hotfix の緊急度と手順が変わる。研修では annotated tag + Release だった
  - [ ] 答え: 

### 環境

- ローカル環境は何か (WSL2 / Mac / Linux / 仮想マシン)。エディタに指定はあるか
  - 聞く理由: 手順書が別の OS 前提だと、コマンドをそのまま打てない
  - [ ] 答え: 
- Docker はどう使われているか (用意された compose を動かすだけか。Dockerfile を書く側か)
  - 聞く理由: 「動かすだけ」なら初日に動けばよい。「書く側」なら学ぶ順序に入れる
  - [ ] 答え: 
- 環境変数や秘密情報 (API キー、DB のパスワード) はどう受け取るか
  - 聞く理由: 経路を知らないと `.env` を作れず、動かせない。リポジトリに入れない約束も確認する
  - [ ] 答え: 
- 2FA や SSO の設定は何が要るか (GitHub / GitLab の組織への参加。VPN)
  - 聞く理由: 設定が終わるまで clone もできない。初日の午前に片づける
  - [ ] 答え: 

### 仕事の進め方

- タスクはどこで管理されているか (Issues か別ツールか)。自分のタスクはどこを見れば分かるか
  - 聞く理由: PR と Issue の紐づけ方 (`Closes #NN` など) が変わる
  - [ ] 答え: 
- 質問はどの経路で聞くか (チャットのどこ。口頭。Issue のコメント)。返事はどのくらいで来るか
  - 聞く理由: 「何分詰まったら聞くか」の目安を決めるため。研修では各演習の「詰まったら」に書いてあった
  - [ ] 答え: 
- 最初に読むリポジトリとドキュメントはどれか
  - 聞く理由: README が古い現場もある。「今の正はどこか」を人に聞くのが早い
  - [ ] 答え: 

## 既定との差分の埋め方

この研修の既定と現場の答えを並べ、変わる操作を書く。「変わる操作」の列は例。現場の答えに合わせて書き換える。

| 項目 | この研修の既定 | 現場の答え | 変わる操作 (例) |
|---|---|---|---|
| ブランチ運用 | GitHub Flow (topic -> PR -> main) | | `develop` があるなら、切る元と PR の向き先を `develop` にする。git-flow なら release / hotfix ブランチの切り方を聞く |
| ブランチ名 | `quest/NN-<slug>` | | チケット番号が必須なら `feature/PROJ-123-<slug>` のように。接頭辞を CI が見ていないか確認する |
| マージ方式 | Squash and merge | | squash が使えないなら、ローカルで `git rebase -i` してコミットを 1 つにまとめてから push する。merge commit なら 1 コミットずつ読める粒度にする |
| PR 本文 | 5 項目 (意図 / 変更内容 / 影響範囲 / 確認方法 / 相談したいこと) | | テンプレートがあればそれに従う。無ければ 5 項目をそのまま使ってよい |
| PR タイトル | `quest-NN: <動詞で始まる要約>` | | チケット番号を頭に付ける規約が多い。Conventional Commits なら `feat:` / `fix:` で始める (squash のコミットメッセージになる) |
| レビュー | approve 1 人。会話の解決が必須 | | 2 人必須なら 2 人目を待つ。approve が必須でない現場では「レビュー済み」の合図を聞く |
| コミットメッセージ | 自由 (squash で PR タイトルに置き換わる) | | 規約があればコミット単位で守る。squash されない現場では `wip` を残さない |
| CI | PR の Checks タブで `check` を見る | | ジョブ名と見る場所を聞く。赤いときに聞く相手を決める |
| 質問の目安 | 演習ごとに「詰まったら」に書いてある分数 | | 現場の目安に置き換える。聞く経路も書く |

初日に聞けなかったら、PR を 1 本出す前に聞く。
